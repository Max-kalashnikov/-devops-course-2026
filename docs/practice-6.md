# Практическая работа 6

## Цель

Опубликовать статический сайт через Nginx с HTTPS, безопасно доставлять его
из чистого Git-коммита и диагностировать ошибки доступа и HTTP.

## Выполнение

Команды установки и настройки - раздел 8 `server-setup.md`. Сначала стандартный
HTTP-сайт и placeholder, затем свой server-блок, сертификат с SAN и редирект,
далее rsync, скрипт деплоя, опыты с правами и журналами. После HTTPS создать
04-nginx-https. Ветку feature/web-deploy слить через PR до работы 7.

## Пять проверок deploy.sh

Проводить в учебном репозитории с настроенным SSH и ~/devops.crt.
Код возврата фиксировать сразу: `bash scripts/deploy.sh; echo $?`.

1. На чистой копии запустить `bash scripts/deploy.sh --dry-run`: ожидается 0,
   план rsync, отсутствие изменения сервера и отсутствие проверки HTTP.
2. Изменить текст сайта, создать коммит, выполнить обычный запуск: ожидается 0,
   короткий хеш и новое содержимое. Повторить запуск из каталога docs по
   `bash ../scripts/deploy.sh`: путь вычисляется относительно самого скрипта.
3. Изменить HTML без коммита: ожидается 1 до rsync. Проверить и вариант
   `git add site/index.html` без коммита. Затем сохранить изменение коммитом.
4. В отдельной сессии VM `sudo systemctl stop nginx`. На чистой копии
   выполнить деплой: rsync проходит, curl завершается ошибкой, итоговый код 1.
   Сразу восстановить `sudo systemctl start nginx`.
5. Временно переименовать index.html и зафиксировать коммит. Ожидается 1 до
   синхронизации, серверная главная страница сохраняется. Вернуть файл новым
   коммитом. На общей ветке использовать revert, не переписывать историю.

## Права и TLS

При devops:devops, каталогах 755 и файлах 644 пользователь www-data читает
содержимое через категорию others, но не создаёт и не меняет файлы. На ключе
600 root:root, на сертификате 644 root:root. Главный процесс Nginx работает
от root, загружает ключ и создаёт рабочие процессы; запрет чтения ключевого файла
у www-data не мешает штатному TLS. Компрометация процесса всё же опасна.

Для самоподписанного сертификата subject и issuer совпадают; это полезный
признак, но криптографически самоподпись подтверждается проверкой подписи его
публичным ключом. SAN должен содержать DNS:devops.local. Доверие для curl
задаётся сертификатом, полученным через проверенный SSH, с `--cacert`.

## Опыты с правами

Держать открытым `sudo tail -f /var/log/nginx/devops-site.error.log`.
После каждого опыта возвращать 755 для каталога и 644 для index.html.
Ниже ожидаемая таблица; фактические коды и строки журнала фиксируются на VM.

| Каталог | others | Ожидаемый HTTP | Причина |
| --- | --- | --- | --- |
| 755 | r-x | 200 | Можно найти и прочитать файл |
| 750 | --- | 403 | Нет обхода каталога |
| 744 | r-- | 403 | Можно прочитать имена, но нельзя обратиться к объекту |
| 711 | --x | 200 | Известное имя доступно без перечисления |

При chmod 600 index.html ожидается 403 из-за запрета чтения файла. Точная
формулировка ошибки при try_files зависит от этапа, на котором Nginx встретил
запрет. Сопоставить реальную запись с `namei -l` и проверками от www-data.

Для опыта подмены установить 666 у исходного HTML и доставить без --chmod;
проверить `find /var/www/devops-site -perm -o+w` и изменить файл от www-data
командой из методички. Подмена возможна из-за записи для others; в реальной
системе такой доступ мог бы использовать нарушитель после RCE в веб-процессе.
Штатный deploy.sh восстанавливает содержимое и права через --chmod=D755,F644.

## Анализ HTTP и журналов

На хосте `curl -v --cacert ~/devops.crt https://devops.local`:
звёздочки описывают TLS, `>` - запрос, `<` - ответ. Зафиксировать фактическую
версию TLS и заголовки Server, Content-Type, Content-Length.

Сделать три запроса `/`, запросы `/admin`, `/wp-login.php`, `/.env` и HTTP `/`.
В combined access log разобрать IP, время в квадратных скобках, метод и URI,
код, размер тела, Referer и User-Agent. Распределение:

```bash
sudo awk '{print $9}' /var/log/nginx/devops-site.access.log | sort | uniq -c | sort -rn
```

Поиски /.env нацелены на утечки секретов, /wp-login.php - на вход WordPress.
Журнал показывает источник, время, путь, статус и агент, но сам по себе не
доказывает личность нарушителя. Эти обращения типичны для фонового сканирования.
Числа распределения брать из реального журнала, включая прежние запросы.

## Расширение аудита

`bash audit.sh 6` проверяет активность и синтаксис Nginx, срок сертификата,
отсутствие записи для всех и права ключа 600. На VM выполнить успешный запуск,
затем `CERT_MIN_SECONDS=40000000 bash audit.sh 6` (порог выше срока в 365 дней)
и запуск с chmod 666 index.html. Ожидаемые коды 0, 1, 1.
После проверки вернуть 644. При штатном запуске порог - 2592000 секунд.

## Ответы на контрольные вопросы

1. Запрос содержит стартовую строку (метод, цель, версия), заголовки, пустую
   строку и необязательное тело. Ответ - версию, код/фразу, заголовки и тело.
   Nginx учитывает адрес/порт, имя SNI для TLS и Host для запроса; при отсутствии
   совпадения используется default_server соответствующего сокета или первый блок.
2. 301 - постоянный перенос, 302 - временный. Для постоянного HTTPS выбран 301;
   клиенты могут кэшировать его. Для строгого сохранения метода полезны 307/308.
3. Перед применением нужна `nginx -t`. reload плавно перечитывает настройки и
   при неудаче обычно сохраняет старых работников; restart сначала останавливает
   службу и при невалидной конфигурации не сможет запустить её.
4. sites-available хранит конфигурации, sites-enabled - ссылки активных ресурсов.
   Удалить только ссылку, проверить nginx -t и выполнить reload.
5. Главный процесс открывает привилегированные порты и читает ключ. Рабочие
   процессы обслуживают запросы с уменьшенными полномочиями. Они получают
   необходимый TLS-контекст при штатном запуске, не читая ключевой файл сами.
6. Канал шифруется и защищается от изменения; подлинность неизвестного сервера
   без отдельного доверия не подтверждена. В работе доверенный сертификат получен
   по SSH и передан curl через --cacert. Современная проверка имени использует
   SAN; одного CN недостаточно.
7. Клиент помнит HSTS и запрещает обход ошибок сертификата. Установить доверие
   к новому корректному сертификату на клиенте либо удалить локальную HSTS-запись
   в учебной среде. Удаление заголовка на сервере не стирает уже сохранённую политику.
8. $host не содержит исходный нестандартный порт: редирект ведёт на
   https://localhost/ (443 хоста), а требуется 8443. Host-only даёт прямой
   доступ к стандартным портам VM по собственному адресу и имени.
9. Нет x на одном из родительских каталогов; проверить `namei -l`.
   Каталог 711 допускает поиск известного имени, 744 не допускает обход.
10. devops может доставлять файлы без root. www-data получает только чтение.
    Запись для веб-процесса позволила бы менять сайт после эксплуатации приложения.
11. Без завершающего `/` копируется каталог site внутрь назначения, возникает
    /var/www/devops-site/site. --delete удаляет лишние объекты внутри переданного
    дерева site, а не автоматически корневой index.html соседнего дерева.
12. --chmod нормализует права назначения. Без него 600 может сделать сайт
    нечитаемым, а 666/777 - разрешить подмену файлов посторонним процессом.
13. Сработал ufw limit из-за частых новых SSH-соединений. Свести операции в одно
    соединение (как deploy.sh) либо использовать SSH multiplexing; также выдерживать
    интервалы запуска. Не добавлять безусловный allow поверх LIMIT.
14. -e завершает сценарий при необработанных ошибках с оговорками Bash,
    -u выявляет необъявленные переменные, pipefail распространяет ошибки pipeline.
    curl -f считает HTTP-ошибки неуспехом. CI ориентируется на exit code, поэтому
    ложный 0 скрывает неуспешную доставку.

## Факультативный атомарный деплой

Не входит в обязательную часть. Для него нужны releases и ссылка current,
rsync --link-dest, не более пяти версий, переключение через временную ссылку
и `mv -T` в пределах одной файловой системы. `ln -sfn` может сначала удалить
старую ссылку и оставить промежуток без current; rename через mv атомарно
заменяет имя. Реализация стандартного deploy.sh намеренно соответствует
основному заданию с непосредственной синхронизацией каталога.
