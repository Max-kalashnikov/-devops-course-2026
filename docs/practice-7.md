# Практическая работа 7

## Цель

Запустить Flask и PostgreSQL в Docker Compose, сохранить данные в именованном
томе, ограничить публикацию портов и предоставить HTTPS через Nginx.

## Образ и запуск без БД

Установка Docker и доставка - раздел 9 `server-setup.md`. На VM:

```bash
cd ~/app
docker build -t devops-app:1.0 .
docker image ls devops-app
docker history devops-app:1.0
docker run -d --name app-test -p 127.0.0.1:5000:5000 devops-app:1.0
curl -i http://127.0.0.1:5000/health
curl -i http://127.0.0.1:5000/
docker logs app-test
docker exec app-test id
docker rm -f app-test
```

Без env по умолчанию DB_HOST=localhost: это сам контейнер, а не VM или соседняя
БД. /health возвращает ok без обращения к базе, `/` ожидаемо даёт 500. В журнале
нужно найти реальную ошибку psycopg2, а не считать успешный /health готовностью БД.
Заменить приветствие в app.py на персональное, доставить и повторить сборку.
COPY requirements.txt и pip install кэшируются; COPY app.py и следующие слои
пересоздаются. Образ запускается от app, исходники принадлежат root и имеют 644.

## Compose и сохранность данных

.env создавать только на VM через init-app-env.sh. Шаблон содержит заглушку,
настоящий пароль формируется openssl, права 600. Секрет исключён и из Git,
и из Docker-контекста; rsync доставляет app с --exclude=.env.

Выполнить `docker compose up -d --build`, `docker compose ps`, три обращения `/`,
`docker compose exec app getent hosts db` и `sudo ss -tlnp`.
Compose DNS разрешает имя сервиса db в общей сети backend. PostgreSQL становится
healthy по pg_isready до запуска app. Приложение слушает 127.0.0.1:5000 на VM,
БД не публикует 5432. Dockerfile EXPOSE документирует порт и не публикует его.

Зафиксировать счётчик; выполнить down и up, дождаться готовности и запросить `/`:
число продолжится. В отдельном учебном опыте down -v удалит том и данные;
после следующего up первый `/` должен показать Visits: 1. Не применять down -v
к другим проектам. Сделать снимок 05-docker-compose.

## Обратный прокси и обход UFW

В учебной VM воспроизвести:

```bash
docker run -d --rm --name exposed -p 5001:5000 devops-app:1.0
sudo ufw status | grep 5001
sudo iptables -t nat -L DOCKER -n | grep 5001
```

С хоста `curl http://devops.local:5001/health`, затем в VM `docker stop exposed`.
На стандартном iptables backend опубликованный Docker-порт может обходить UFW:
DNAT и FORWARD обрабатывают пакет до ожидаемой фильтрации INPUT.
В нашей штатной конфигурации привязка 127.0.0.1:5000 не публикует приложение
на Host-only. БД вообще не имеет ports. Нельзя считать UFW единственной защитой
опубликованных контейнеров. Официальное описание:
https://docs.docker.com/engine/network/packet-filtering-firewalls/

Добавить блок `/app/` из config/nginx-devops-site.conf и применить через
`sudo nginx -t && sudo systemctl reload nginx`. Завершающий `/` в proxy_pass
заменяет префикс: `/app/health` превращается в `/health` upstream.
Проверить `/`, `/app/`, `/app/health` с доверенным сертификатом.

Для опыта 502: `docker compose stop app`, запросить `/app/`, прочитать error log
и восстановить `docker compose start app`. Connection refused к upstream
означает, что клиент смог обратиться к Nginx, но Nginx не смог установить
соединение с приложением на 127.0.0.1:5000. Статический `/` остаётся доступным.

## Аудит и Git

`bash audit.sh 7` добавляет четыре проверки: активность Docker, healthy у БД,
отсутствие внешней публикации 5000/5432, права .env 600. Проверяется и ss,
и вывод Docker: при отключённом docker-proxy публикация через NAT может
не отображаться как отдельный слушающий процесс.

На VM выполнить положительный запуск, временно изменить ports на 5000:5000,
пересоздать сервис и повторить аудит (ожидается 1). После опыта вернуть
127.0.0.1:5000:5000 и пересоздать, убедиться в коде 0. Не оставлять порт открытым.
Зафиксировать Conventional Commit, проверить `git ls-files app/.env` (пусто),
отправить feature/docker, создать PR в main и выполнить слияние.

## Ответы на контрольные вопросы

1. Namespaces изолируют PID, сеть, mount points, hostname и другие ресурсы;
   cgroups ограничивают и учитывают CPU/RAM. Дополняют защиту capabilities,
   seccomp и LSM. Контейнер использует ядро хоста и запускает процесс, поэтому
   не загружает отдельную гостевую ОС, как VM.
2. Docker кэширует слои по инструкции и входным данным. Неизменные requirements
   сохраняют слой pip install; app.py меняет только последующие слои. COPY . .
   перед pip install заставлял бы переустанавливать зависимости при изменении кода.
3. localhost - loopback самого контейнера. В Compose DB_HOST=db, имя разрешается
   встроенным DNS в адрес БД в общей пользовательской сети backend.
4. Простое depends_on задаёт порядок запуска, а service_healthy ждёт успешного
   healthcheck. Это предотвращает стартовый запрос к ещё не готовой БД,
   но не гарантирует доступность БД навсегда и не заменяет обработку ошибок.
5. down удаляет контейнеры и сеть проекта, именованный том остаётся. down -v
   удаляет и том. Тег 16-alpine сохраняет основную версию PostgreSQL;
   latest может перейти на несовместимый формат данных новой основной версии.
6. Docker настраивает маршрутизацию/NAT для опубликованных портов; пакет может
   пройти мимо правил UFW INPUT. Публиковать приложение только на 127.0.0.1,
   наружу отдавать через Nginx. БД не публиковать. Для ограничений внешних
   Docker-портов нужны подходящие правила Docker backend, а не только ufw allow/deny.
7. Участник docker управляет привилегированным daemon и может запустить root-
   контейнер с каталогом хоста, например смонтировав / в /host. Изменение
   /host/etc через него означает изменение файлов хоста с root-полномочиями.
   Поэтому группа docker фактически равна root и обходит обычное ограничение sudo.
8. Причины 502: приложение остановлено или upstream указан неверно (адрес,
   порт, протокол); также возможен некорректный ответ приложения. Проверить
   nginx -t, error log, docker compose ps/logs, локальный curl на 127.0.0.1:5000
   и фактические порты. При upstream timeout типичен 504, а не 502.
