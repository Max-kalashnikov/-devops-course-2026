# Практическая работа 5

## Цель

Подготовить Ubuntu Server для следующих работ: отдельный администратор, ключевой SSH,
ограничение привилегий и входящего трафика, локальное имя и воспроизводимое описание.

## Выполнение

Пошаговые команды находятся в разделах 1–7 `server-setup.md`. Выполнять в порядке:
VM → снимок 01 → пользователь и ключ → снимок 02 → защита SSH → снимок 03 → UFW → имя.
Основной конфигурационный файл SSH сохраняется, настройки оформлены drop-in.
После каждого изменения проверять действующие значения `sshd -T`, порт через `ss`
и новый вход, сохраняя прежнюю сессию. Комментарий в файле не подтверждает настройку.

Скрипт `scripts/audit.sh 5` проверяет запрет root и пароля, нестандартный корректный
порт, MaxAuthTries 3, активный UFW, deny incoming и LIMIT 2222/tcp. Возвращает
0 при успехе всех проверок и 1 при нарушении хотя бы одной. Положительный запуск
и изменение MaxAuthTries на 10 фиксируются на собственной VM; затем вернуть 3.

## Пояснения к экспериментам

`Authentications that can continue` до защиты может содержать publickey,password;
после защиты должен оставаться publickey. Фактический вывод зависит от исходной ОС.
Отказ root связан с PermitRootLogin/AllowUsers; отказ при отключённом клиентском
PubkeyAuthentication связан с отсутствием разрешённого метода аутентификации.
Одинаковое клиентское сообщение Permission denied возможно в обоих случаях:
точную причину нужно сопоставлять с серверным журналом, а не выдумывать различие.

В записи UFW BLOCK поле SRC означает адрес источника, DST - адрес назначения,
PROTO - протокол, DPT - порт назначения (для опыта 8080). Конкретные адреса и
время берутся из реального журнала.

## Ответы на контрольные вопросы

1. NAT подменяет исходящий адрес и хранит состояние соединений, но не знает,
   какому гостю направить произвольное входящее соединение. Нужен проброс.
   Host-only создаёт общий виртуальный сегмент хоста и гостя с прямой адресацией.
2. known_hosts хранится у клиента и связывает узел с ключом сервера.
   authorized_keys находится на сервере в домашнем каталоге пользователя и
   перечисляет публичные ключи, которым разрешён вход от его имени.
3. При ключевом входе приватный ключ не передаётся серверу: клиент доказывает
   владение подписью. Случайный ключ трудно перебрать, его можно защитить паролем
   и отозвать отдельно. Кража незашифрованного приватного ключа всё же опасна.
4. allow разрешает подходящие соединения, limit также ограничивает частоту
   новых подключений от источника. Это не заменяет ключевую аутентификацию.
5. Нарушена процедура сохранения доступа: исходную сессию закрыли до проверки
   нового входа. До применения нужны `sudo sshd -t`, после применения -
   `sudo ss -tlnp | grep sshd` и новый `ssh` в другом терминале. Две локальные
   проверки уменьшают риск, но сами по себе не проверяют NAT и firewall.
6. На ufw enable новые входящие SSH-соединения будут запрещены; текущая сессия
   может сохраниться благодаря правилу established. Методичка описывает риск
   блокировки как немедленный, но поведение текущего соединения зависит от
   состояния правил. Правильный порядок: политики → разрешение управляющего
   порта → enable → проверка отдельного соединения.
7. Имя ssh разрешается по `/etc/services` в порт 22. После переноса нужен
   `ufw limit 2222/tcp`, а не символьное имя ssh.
8. Нестандартный порт уменьшает фоновый шум автоматических атак на 22 и объём
   журналов. Он не скрывает службу от целевого сканирования и не заменяет ключи,
   запрет root, обновления и ограничения доступа.
9. Причины: переустановка сервера, замена VM/адреса или атака посредника.
   Сверить fingerprint с доверенной консолью. Только при подтверждённой штатной
   замене удалить старую запись. Безусловный ssh-keygen -R уничтожает признак
   подмены и превращает следующую атаку в «первое подключение».
10. Другие локальные пользователи или процессы с доступом к файлу могут украсть
    ключ и выдать себя за владельца. Проверка прав ограничивает локальную утечку;
    принадлежность файла пользователю не означает, что остальные не могут читать.
11. ping обычно использует getaddrinfo и NSS по `/etc/nsswitch.conf`: порядок
    определяется строкой hosts, часто files, resolve/mdns, dns с условиями возврата.
    `/etc/hosts` может успешно разрешить имя без DNS. dig напрямую обращается
    к DNS и не использует всю NSS-цепочку. Для .local возможен mDNS; универсального
    фиксированного порядка без чтения nsswitch.conf нет.
12. 127.0.0.1 в цели - loopback SSH-сервера. Между хостами трафик идёт внутри SSH
    по 2222; sshd сам соединяется с локальным 8080. Внешний вход на 8080 не нужен.
    Флаг -N не запускает удалённую оболочку.
13. После sudo su - журнал sudo может содержать только запуск оболочки,
    а не последующие команды. Нужны персональные учётные записи, ограниченные
    sudoers, запрет общего root-shell где возможно и централизованный аудит
    с записью ввода/вывода sudo или auditd. История shell не надёжный аудит.
14. На многих узлах ручная настройка приводит к расхождению конфигураций,
    плохо масштабируется и затрудняет массовый откат/проверку изменений.
    Ansible хранит желаемое состояние в коде, повторяет операции и показывает diff.

## Подготовка к работе 6

Nginx принимает HTTP, выбирает виртуальный хост по имени и отдаёт файлы либо
проксирует запросы. Forward proxy представляет клиента перед внешними серверами
(например, корпоративный доступ). Reverse proxy представляет серверы перед клиентом
(например, Nginx перед Flask). TLS согласует параметры шифрования и проверяет
сертификат; сервер доказывает владение закрытым ключом. Самоподписанный сертификат
шифрует канал, но требует отдельного доверенного способа подтверждения подлинности.

## Дополнительный опыт с туннелем

В VM создать каталог restricted и запустить `python3 -m http.server 8080 --bind 127.0.0.1`.
На хосте подтвердить недоступность внешнего 8080, затем выполнить
`ssh -L 9090:127.0.0.1:8080 -N devops` и открыть http://localhost:9090.
Это факультативное задание. Итоговое обоснование - ответ 12 выше.
